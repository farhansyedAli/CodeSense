Where does Django validate user passwords before saving to the database?
CS
CodeSense · 3 sources

Password validation runs through a pipeline defined in 📄 password_validation.py:45 before any save operation.

The entry point is validate_password(), which iterates over every validator listed in your AUTH_PASSWORD_VALIDATORS setting:

django/contrib/auth/password_validation.py · line 45 
def validate_password(password, user=None, password_validators=None):
    """Run all validators and raise ValidationError on failure."""
    errors = []
    if password_validators is None:
        password_validators = get_default_password_validators()
    for validator in password_validators:
        try:
            validator.validate(password, user)
        except ValidationError as error:
            errors.append(error)
    if errors:
        raise ValidationError(errors)

This function is called from 📄 forms.py:163 inside SetPasswordForm.clean_new_password2(), which runs before the model's save() is ever invoked.

The actual hashing (not validation) happens separately in 📄 hashers.py:28 via make_password().

Is there any SQL injection risk in the ORM query builder?
CS
CodeSense · security scan + 2 sources

The ORM's parameterized query layer in 📄 compiler.py:412 is safe by default — all values are passed as parameters, never interpolated into SQL strings.

However, one pattern was flagged by the static analysis layer:

⚠️
Raw SQL via .extra() — medium severity
📄 query.py:891 — The .extra(where=...) method accepts raw SQL strings. If user input reaches this parameter without sanitization, SQLi is possible. This path is reachable from public API endpoints in apps that use .extra() directly.

This is a known Django footgun, documented in their own security guide. The fix is to use .raw() with parameterized queries or avoid .extra() entirely.
